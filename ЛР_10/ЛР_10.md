### 1.4. Відповіді на питання

**4.1. Яке призначення команди `id`?**

Команда `id` виводить ідентифікаційну інформацію поточного користувача (або вказаного як аргумент): UID і ім'я користувача, GID і назву основної групи, а також GID та імена всіх додаткових груп. Вона дозволяє перевірити, під яким обліковим записом працює користувач, до яких груп належить, і переконатися, що `newgrp` змінила основну групу. Приклад:

```bash
$ id
uid=1001(sysadmin) gid=1001(sysadmin) groups=1001(sysadmin),4(adm),27(sudo),1005(research),1006(development)
```

**4.2. Як переглянути, які права доступу має власник файлу?**

Командою `ls -l` (для каталогу самого по собі - `ls -ld`). Перший символ рядка - тип файлу, наступні дев'ять - три трійки прав: власника (user), групи (group) та інших (others). Права власника - символи 2–4:

```bash
$ ls -l script.sh
-rwxr-x--- 1 user1 team 45 Nov 20 10:15 script.sh
```

Тут власник `user1` має `rwx` (читання, запис, виконання). Докладніше можна переглянути командою `stat script.sh` - вона показує права і у вісімковому вигляді (`0750`).

**4.3.\* Як змінити власника групи?**

Для зміни групи-власника файлу використовують `chgrp` або `chown` із двокрапкою:

```bash
chgrp team file.txt          # змінити групу на team
chown :team file.txt         # те саме через chown
chown user2:team file.txt    # змінити і власника, і групу
chgrp -R team dir/           # рекурсивно для каталогу
```

Звичайний користувач може змінити групу лише власним файлам і лише на ту групу, до якої він сам належить. Змінити власника-користувача (`chown`) може тільки root (через `sudo`). Також для **нових** файлів основну групу тимчасово змінюють командою `newgrp group_name`.

**4.4.\* Як переглянути в терміналі тип поточного файлу? Приклади для різних типів.**

Є три основні способи:

1. `ls -l` - перший символ у рядку прав задає тип.
2. `file <ім'я>` - визначає тип за вмістом, людською мовою.
3. `stat <ім'я>` - показує поле `File:` / `Size:` / тип у рядку `regular file`, `directory` тощо.

| Символ | Тип файлу | Приклад |
|---|---|---|
| `-` | звичайний файл (regular file) | `-rw-r--r-- ... /etc/passwd` |
| `d` | каталог (directory) | `drwxr-xr-x ... /home` |
| `l` | символічне посилання (symbolic link) | `lrwxrwxrwx ... /bin -> usr/bin` |
| `c` | символьний пристрій (character device) | `crw-rw-rw- ... /dev/null`, `/dev/tty` |
| `b` | блоковий пристрій (block device) | `brw-rw---- ... /dev/sda` |
| `p` | іменований канал (named pipe, FIFO) | створюється `mkfifo mypipe` |
| `s` | сокет (socket) | `srw-rw-rw- ... /run/dbus/system_bus_socket` |

```bash
$ file /etc/passwd
/etc/passwd: ASCII text
$ file /bin/ls
/bin/ls: ELF 64-bit LSB pie executable, x86-64 ...
$ file /home
/home: directory
```

**4.5.\*\* Для чого використовуються дозволи setuid та setgid?**

Це спеціальні (special) права, які потрібні, коли звичайних `r`, `w`, `x` недостатньо.

- **setuid** на виконуваному файлі: програма запускається з правами **власника файлу**, а не того, хто її запустив. Позначається `s` замість `x` у трійці власника. Класичний приклад - `/usr/bin/passwd`: власник root, тому звичайний користувач може змінити свій пароль, тобто записати в `/etc/shadow`, до якого сам доступу не має. Встановлення: `chmod u+s file` або `chmod 4755 file`.
- **setgid** на виконуваному файлі: програма виконується з правами **групи-власника файлу**. Приклад - `/usr/bin/wall` (група `tty`), яка пише у файли терміналів `/dev/pts/*`. Позначається `s` у трійці групи.
- **setgid на каталозі**: усі нові файли й підкаталоги, створені в ньому, автоматично належать групі каталогу (а не основній групі творця), а нові підкаталоги ще й успадковують setgid. Це зручно для спільних проєктних каталогів. Встановлення: `chmod g+s dir` або `chmod 2775 dir`.

Велика `S` / `S` означає, що спеціальний біт встановлено, але звичайного `x` немає - тоді він фактично не діє.

**4.6.\*\* Для чого потрібен «липкий біт» (sticky bit)? Приклади використання.**

Sticky bit, встановлений на **каталозі**, забороняє видаляти та перейменовувати файли в цьому каталозі всім, окрім власника файлу, власника каталогу та root, - навіть якщо в користувача є право запису (`w`) на сам каталог. Позначається `t` замість `x` у трійці others (велика `T`, якщо `x` немає). Встановлення: `chmod +t dir` або `chmod 1777 dir`.

Приклади, коли доцільно використовувати:

- `/tmp` і `/var/tmp` - `drwxrwxrwt`: усі можуть створювати тимчасові файли, але не можуть стирати чужі.
- Спільний каталог проєкту, де кілька користувачів пишуть, але не повинні видаляти файли колег (разом із setgid: `chmod 3770 dir`).
- Каталог для вивантаження файлів на файловому сервері (upload/drop box).

### 2.3. Практичні завдання

> Скріншоти не додаються; нижче наведено команди та очікуваний результат виконання. Імена користувачів: `user1`, `user2`, `user3`.

#### 2.3.1. Створення трьох користувачів

```bash
sudo useradd -m -s /bin/bash user1
sudo useradd -m -s /bin/bash user2
sudo useradd -m -s /bin/bash user3
sudo passwd user1      # аналогічно для user2 і user3
sudo passwd user2
sudo passwd user3
getent passwd user1 user2 user3
```

Очікуваний результат:

```
user1:x:1001:1001::/home/user1:/bin/bash
user2:x:1002:1002::/home/user2:/bin/bash
user3:x:1003:1003::/home/user3:/bin/bash
```

#### 2.3.2. Створення групи та додавання двох користувачів

```bash
sudo groupadd team
sudo usermod -aG team user1
sudo usermod -aG team user2
getent group team
id user1
```

Очікуваний результат:

```
team:x:1004:user1,user2
uid=1001(user1) gid=1001(user1) groups=1001(user1),1004(team)
```

`user3` у групу `team` не входить - він виступатиме як представник категорії others.

#### 2.3.3. Файл (скрипт): права для власника, групи та інших

```bash
sudo su - user1                          # працюємо від імені user1
echo -e '#!/bin/bash\necho "Hello from script"' > script.sh
chmod 700 script.sh                      # власник: rwx
ls -l script.sh
```

```
-rwx------ 1 user1 user1 39 Nov 20 10:15 script.sh
```

Зміна групи та прав для групи (перегляд і виконання, без редагування):

```bash
chgrp team script.sh
chmod g+rx script.sh                     # або: chmod 750 script.sh
ls -l script.sh
```

```
-rwxr-x--- 1 user1 team 39 Nov 20 10:15 script.sh
```

Для інших (others) доступ заборонено - `chmod o-rwx` (у нашому випадку їх прав уже немає, що видно з `---` в кінці):

```bash
chmod o-rwx script.sh
ls -l script.sh
```

```
-rwxr-x--- 1 user1 team 39 Nov 20 10:15 script.sh
```

Перевірка від імені інших користувачів. Щоб побачити файл, переносимо його у спільне місце, яке мають змогу пройти всі: `/tmp`.

```bash
cp -p script.sh /tmp/script.sh           # -p зберігає права, власника
exit                                      # повернення до основного користувача

sudo -u user2 /tmp/script.sh              # user2 належить до team → виконується
sudo -u user2 bash -c 'echo x >> /tmp/script.sh'   # спроба редагування групою
sudo -u user3 cat /tmp/script.sh          # user3 - others
```

```
Hello from script
bash: /tmp/script.sh: Permission denied
cat: /tmp/script.sh: Permission denied
```

Висновок: група (`user2`) може переглядати й виконувати, але не редагувати файл; інші (`user3`) не мають жодного доступу.

#### 2.3.4.\* Те саме для каталогів

```bash
sudo mkdir /srv/for_all /srv/only_owner /srv/group_read
```

1. Каталог, доступний усім трьом користувачам (всі можуть переглядати, входити та створювати файли):

```bash
sudo chmod 777 /srv/for_all
```

2. Каталог, доступний лише власнику (`user1`):

```bash
sudo chown user1:user1 /srv/only_owner
sudo chmod 700 /srv/only_owner
```

3. Каталог, який користувачі групи власника можуть переглядати, але не редагувати:

```bash
sudo chown user1:team /srv/group_read
sudo chmod 750 /srv/group_read
```

```bash
ls -ld /srv/for_all /srv/only_owner /srv/group_read
```

```
drwxrwxrwx 2 root  root  4096 Nov 20 10:20 /srv/for_all
drwxr-x--- 2 user1 team  4096 Nov 20 10:20 /srv/group_read
drwx------ 2 user1 user1 4096 Nov 20 10:20 /srv/only_owner
```

Перевірка:

```bash
sudo -u user3 touch /srv/for_all/u3.txt       # успішно, створено
sudo -u user2 ls /srv/only_owner              # ls: cannot open directory: Permission denied
sudo -u user2 ls /srv/group_read              # успішно (група team: r-x)
sudo -u user2 touch /srv/group_read/a.txt     # touch: cannot touch: Permission denied
sudo -u user3 ls /srv/group_read              # Permission denied (others не мають прав)
```

#### 2.3.5.\* Файл `emptyfile` і числовий метод `chmod`

```bash
touch emptyfile
chmod 000 emptyfile
ls -l emptyfile
```

```
---------- 1 user1 user1 0 Nov 20 10:30 emptyfile
```

Передаємо **одну цифру**:

```bash
chmod 4 emptyfile
ls -l emptyfile
```

```
-------r-- 1 user1 user1 0 Nov 20 10:30 emptyfile
```

Передаємо **дві цифри**:

```bash
chmod 44 emptyfile
ls -l emptyfile
```

```
----r--r-- 1 user1 user1 0 Nov 20 10:30 emptyfile
```

**Що ми дізнаємося про зчитування числового значення `chmod`:** цифри читаються **справа наліво**: остання цифра завжди належить категорії others, передостання - group, третя з кінця - user, четверта - спеціальні біти. Відсутні старші цифри `chmod` доповнює нулями зліва. Тому `chmod 4` дорівнює `004` (`-------r--`, право читання лише в інших), а `chmod 44` - `044` (`----r--r--`, читання для групи й інших, власник без прав). Це також означає, що `chmod 4 file` - небезпечна помилка: власник файлу втрачає доступ, а решта отримує його.

#### 2.3.6.\*\* Каталог із автоматичною групою та захистом від видалення чужих файлів

Потрібна комбінація **setgid** (нові файли автоматично належать групі каталогу) та **sticky bit** (видаляти файл може лише його творець):

```bash
sudo mkdir /srv/shared
sudo chown root:team /srv/shared
sudo chmod 3770 /srv/shared              # 2000 (setgid) + 1000 (sticky) + 770
ls -ld /srv/shared
```

```
drwxrws--T 2 root team 4096 Nov 20 10:40 /srv/shared
```

Позначення: `s` у трійці групи - setgid, `T` у трійці others - sticky bit (велика, бо `x` для others немає - це відповідає `770`).

Перевірка:

```bash
sudo -u user1 touch /srv/shared/f_user1.txt
ls -l /srv/shared
```

```
-rw-r--r-- 1 user1 team 0 Nov 20 10:41 f_user1.txt     # група team, а не user1 - працює setgid
```

```bash
sudo -u user2 rm /srv/shared/f_user1.txt
```

```
rm: cannot remove '/srv/shared/f_user1.txt': Operation not permitted    # працює sticky bit
```

Власник файлу (`user1`) видаляє свій файл без проблем:

```bash
sudo -u user1 rm /srv/shared/f_user1.txt
```
#### 2.3.7.\*\* Файли, жорсткі та символічні посилання під кожним користувачем

Щоб усі троє могли працювати в одному місці й водночас перевірити поведінку sticky bit, використаємо каталог `/srv/links` з правами `1777`:

```bash
sudo mkdir /srv/links
sudo chmod 1777 /srv/links
```

Кожен користувач створює файл, жорстке та символічне посилання:

```bash
for u in user1 user2 user3; do
  sudo -u $u bash -c "
    cd /srv/links
    echo 'data of $u' > file_$u.txt
    ln file_$u.txt hard_$u.txt
    ln -s file_$u.txt soft_$u.txt
  "
done
ls -li /srv/links
```

Очікуваний результат (однаковий inode у `file_*` і `hard_*`, кількість посилань 2, а символічне посилання має власний inode і довжину, що дорівнює довжині шляху):

```
1310721 -rw-r--r-- 2 user1 user1 14 Nov 20 10:50 file_user1.txt
1310721 -rw-r--r-- 2 user1 user1 14 Nov 20 10:50 hard_user1.txt
1310722 lrwxrwxrwx 1 user1 user1 14 Nov 20 10:50 soft_user1.txt -> file_user1.txt
1310723 -rw-r--r-- 2 user2 user2 14 Nov 20 10:50 file_user2.txt
1310723 -rw-r--r-- 2 user2 user2 14 Nov 20 10:50 hard_user2.txt
1310724 lrwxrwxrwx 1 user2 user2 14 Nov 20 10:50 soft_user2.txt -> file_user2.txt
... (аналогічно для user3)
```

# Єршов Олексій

#### 2.3.8.\*\* Перегляд файлів іншими користувачами

```bash
sudo -u user2 cat /srv/links/file_user1.txt
sudo -u user2 cat /srv/links/hard_user1.txt
sudo -u user2 cat /srv/links/soft_user1.txt
sudo -u user3 cat /srv/links/file_user2.txt
```

```
data of user1
data of user1
data of user1
data of user2
```

Файли мають права `644`, тому інші користувачі можуть читати їх і через оригінал, і через жорстке, і через символічне посилання.

#### 2.3.9.\*\* Спроба видалення чужих файлів іншими користувачами

```bash
sudo -u user2 rm /srv/links/file_user1.txt
sudo -u user2 rm /srv/links/hard_user1.txt
sudo -u user2 rm /srv/links/soft_user1.txt
```

```
rm: cannot remove '/srv/links/file_user1.txt': Operation not permitted
rm: cannot remove '/srv/links/hard_user1.txt': Operation not permitted
rm: cannot remove '/srv/links/soft_user1.txt': Operation not permitted
```

Видалення неможливе, незважаючи на те, що в `user2` є право запису в каталог (`777`) - завдяки **sticky bit**.

Для порівняння: якщо створити такі самі файли в звичайному каталозі з правами `777` **без** sticky bit, будь-який користувач зможе видалити чужі файли (бо право видалення визначається правом запису в каталог, а не правами самого файлу). А в домашньому каталозі `/home/user1` (права `750` або `700`) інші користувачі взагалі не зможуть навіть переглянути вміст.

**Висновки до п. 2.3.7–2.3.9:**

1. Жорстке посилання - це друге ім'я того самого inode (однаковий inode, лічильник посилань 2), а символічне - окремий файл зі шляхом до цілі.
2. Права читання й запису визначаються правами inode: через жорстке посилання діють ті ж права, що й через оригінал; через символічне - права цілі.
3. Можливість видалення файлу залежить від прав **на каталог** (право `w`) та, якщо встановлено sticky bit, від того, чи є користувач власником файлу чи каталогу.

## 3. Відповіді на контрольні запитання

**1. Приклади зміни прав доступу символічним методом (Symbolic Method).**

Синтаксис: `chmod [u|g|o|a][+|-|=][r|w|x] file`. Літери: `u` - user, `g` - group, `o` - others, `a` - all; `+` додає, `-` забирає, `=` задає точно.

```bash
chmod u+x script.sh          # додати власнику право виконання
chmod g-w file.txt           # забрати у групи право запису
chmod o-rwx file.txt         # забрати всі права в інших
chmod a+r file.txt           # дозволити читання всім
chmod u=rwx,g=rx,o= file.txt # власник rwx, група r-x, інші нічого
chmod g+s dir                # setgid на каталог
chmod +t dir                 # sticky bit
```

**2. Приклади зміни прав доступу числовим (octal) методом.**

Значення: `r = 4`, `w = 2`, `x = 1`; цифра - сума для категорії (user, group, others).

```bash
chmod 755 script.sh   # rwxr-xr-x
chmod 644 file.txt    # rw-r--r--
chmod 640 file.txt    # rw-r-----
chmod 700 dir         # rwx------
chmod 4755 file       # setuid + rwxr-xr-x
chmod 2775 dir        # setgid + rwxrwxr-x
chmod 1777 dir        # sticky bit + rwxrwxrwx
chmod 3770 dir        # setgid + sticky + rwxrwx---
```

**3. Яке призначення команди `umask`?**

`umask` (user file-creation mode mask) задає маску, яка **забирає** права у новостворюваних файлів і каталогів. Команда без аргументів показує поточну маску, з аргументом - встановлює нову:

```bash
$ umask
0022
$ umask 027
```

Маска віднімається від базових прав: для файлів - від `666`, для каталогів - від `777`.

**4. Порівняйте жорсткі та символічні посилання.**

| Критерій | Hard link | Symbolic (soft) link |
|---|---|---|
| Що це | ще одне ім'я для того самого inode | окремий файл із власним inode, що містить шлях до цілі |
| Команда | `ln target link` | `ln -s target link` |
| Inode | такий самий, як у оригіналу | власний |
| Файлова система | лише в межах однієї ФС | може вказувати на іншу ФС |
| Каталоги | зазвичай не можна (лише root у деяких системах) | можна |
| Видалення оригіналу | дані лишаються доступними через жорстке посилання | посилання «бите» (dangling) |
| Розмір | як у файлу | довжина шляху до цілі |
| Тип у `ls -l` | `-` (звичайний файл) | `l` |
| Права | спільні з оригіналом | права самого посилання завжди `rwxrwxrwx`, діють права цілі |

**5.\* Чи можна виконати файл із правами лише на виконання (`--x`)?**

Залежить від типу файлу. **Скомпільовану програму** (бінарний файл ELF) можна виконати: ядро завантажує її саме, право читання користувачу не потрібне. **Скрипт** (`#!/bin/bash`, Python тощо) з правом лише `--x` виконати **не вдасться**: інтерпретатор (`bash`) мусить прочитати вміст файлу, а права читання немає, тому виникне `Permission denied`. Для каталогу право `x` без `r` дозволяє входити в нього й звертатися до файлів, якщо знати їхні імена, але не дозволяє переглядати список файлів.

**6.\* Чи збережуться змінені права доступу в наступній сесії?**

**Так.** Права доступу та власник зберігаються в метаданих файлу (inode) у файловій системі, тому вони не залежать від сесії та переживають перезавантаження. Натомість змінене значення `umask` у терміналі діє **лише в поточній сесії** оболонки; щоб зберегти його, команду `umask` потрібно додати до `~/.bashrc`, `~/.profile` або `/etc/profile`. Так само тимчасовим є й перехід в іншу основну групу через `newgrp` - він діє до виходу (`exit`) з нової оболонки.

**7.\* Чи є шаблон прав за замовчуванням при створенні файлів? Як його змінити?**

Так, права за замовчуванням формуються з базових прав мінус `umask`: базові - `666` (`rw-rw-rw-`) для файлів (без `x`, щоб нові файли випадково не ставали виконуваними) і `777` для каталогів. Для типового `umask 022`:

- файли: 666 − 022 = **644** (`rw-r--r--`);
- каталоги: 777 − 022 = **755** (`rwxr-xr-x`).

Для `umask 077` буде 600 і 700 - приватно для власника. Змінити: `umask 027` у поточній сесії або запис у `~/.bashrc` (для користувача) чи `/etc/login.defs` / `/etc/profile` (для всієї системи).

**8.\* Як створити жорстке посилання? Коли доцільно використовувати?**

```bash
ln original.txt hardlink.txt
```

Доцільно: коли потрібна друга назва для файлу без дублювання даних (економія місця), для створення резервних «знімків» у системах на кшталт `rsnapshot`/`rsync --link-dest`, коли файл не має «зникнути», доки існує бодай одне ім'я. Обмеження - лише в межах однієї файлової системи й зазвичай не для каталогів.

**9.\* Як створити символічне посилання? Коли доцільно використовувати?**

```bash
ln -s /шлях/до/цілі symlink
ln -s /usr/bin/python3 /usr/local/bin/python
```

Доцільно: швидкі «ярлики» на довгі шляхи, посилання на каталоги, посилання між різними файловими системами, перемикання версій (`current -> release-2.1`), конфігурації (`/etc/alternatives/...`), а також коли потрібно явно показати, що файл - посилання (видно в `ls -l` як `->`).

**10.\*\* Який каталог правильний для одноразового тимчасового файлу?**

Каталог **`/tmp`**: він доступний для запису всім (`drwxrwxrwt`, з sticky bit, тому користувачі не видаляють чужі тимчасові файли) і очищується під час перезавантаження або періодично. Для тимчасових файлів, які мають пережити перезавантаження, існує `/var/tmp`. У програмах для безпечного створення зазвичай використовують `mktemp`, який створює файл з унікальним іменем у `/tmp`.

**11.\*\* Що відбудеться з іншими файлами, якщо видалити:**

- **файл-оригінал** (`rm original.txt`): **жорстке посилання** продовжує працювати й відкривається з усіма даними (лічильник посилань зменшується з 2 до 1, inode не звільняється); **символічне посилання** стає «битим» (dangling): `cat soft` → `No such file or directory`, бо воно вказує на ім'я, якого вже немає;
- **символічне посилання** (`rm soft`): оригінал і жорстке посилання **не змінюються**, видаляється лише сам маленький файл-посилання;
- **жорстке посилання** (`rm hard`): оригінал і символічне посилання **працюють як раніше**, лічильник посилань inode зменшується на 1; дані видаляться з диска лише тоді, коли буде видалено останнє ім'я і файл не буде відкритий жодним процесом.

## 4. Висновки

У ході лабораторної роботи було вивчено принципи володіння файлами та каталогами в Linux: кожен файл має власника (UID) та групу-власника (GID), які відображаються командами `ls -l`, `id`, `groups`, а змінюються `chown`, `chgrp` і `newgrp`. Опрацьовано два способи керування правами доступу командою `chmod` - символічний (`u+x`, `g-w`) та числовий (`755`, `640`). З'ясовано, що числове значення зчитується справа наліво (others, group, user, спеціальні біти), а відсутні старші цифри доповнюються нулями, тому `chmod 4 file` та `chmod 44 file` дають `004` і `044`. Вивчено роль `umask`: вона визначає права за замовчуванням (666 − umask для файлів і 777 − umask для каталогів) і діє лише в поточній сесії, тоді як самі права файлів зберігаються в inode.

Практично створено трьох користувачів (`user1`–`user3`), групу `team` із двома учасниками, а також файли й каталоги з різними схемами доступу для власника, групи та інших. Продемонстровано, що право читання, запису та виконання працюють по-різному для файлів і каталогів (`x` для каталогу означає можливість входу), а від звичайного файлу з правом лише `--x` скрипт не запускається, бо інтерпретатор має його прочитати.

Також розглянуто спеціальні права: setuid (запуск з правами власника, наприклад `passwd`), setgid (для файлів - права групи, як у `wall`; для каталогів - успадкування групи в нових файлах) та sticky bit (захист від видалення чужих файлів, як у `/tmp`). Їх комбінація `chmod 3770` дає зручний спільний каталог для команди, де файли автоматично належать потрібній групі та не можуть бути видалені іншими учасниками. Експеримент із посиланнями показав, що жорстке посилання - це додаткове ім'я того самого inode (за видалення оригіналу дані зберігаються), а символічне - окремий файл зі шляхом до цілі (після видалення оригіналу стає «битим»). Одержані навички потрібні для адміністрування багатокористувацьких систем і забезпечення безпеки даних у Linux.
