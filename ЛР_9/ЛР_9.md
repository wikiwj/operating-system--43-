# Гапонюк Назар
## Словник термінів (Glossary)

| Term | Переклад / пояснення |
|---|---|
| **root** | суперкористувач (UID 0), має необмежений доступ до системи |
| **sudo** (*superuser do*) | команда для виконання окремих команд з правами адміністратора; дії логуються |
| **su** (*substitute user*) | команда для перемикання на іншого користувача (за замовчуванням root) |
| **privilege** | привілей, право на виконання дії |
| **account** | обліковий запис |
| **system account** | системний обліковий запис для сервісів (UID 1–499 / 1–999), вхід у систему не передбачений |
| **regular user** | звичайний користувач (UID ≥ 1000) |
| **UID / GID** | User ID / Group ID - числові ідентифікатори користувача / групи |
| **primary group** | основна група користувача, вказана в `/etc/passwd` |
| **supplementary group** | додаткова група, визначається в `/etc/group` |
| **UPG** (*User Private Group*) | приватна група користувача: створюється разом з акаунтом, назва збігається з іменем |
| **home directory** | домашній каталог користувача |
| **shell** | командна оболонка користувача (наприклад, `/bin/bash`) |
| **hash** | односторонній криптографічний образ пароля |
| **runlevel** | рівень запуску, функціональний стан системи |
| **login history** | історія входів, файл `/var/log/wtmp` |
| **append** | додати (опція `-a` у `usermod`) |
| **ownership** | належність файлу користувачу та групі |

## Відповіді на завдання попередньої підготовки

### 4.1. Розкрийте поняття UPG, коли їх доцільно використовувати?

**UPG (User Private Group)** - це схема, за якої при створенні нового користувача система автоматично створює для нього окрему групу з тим самим іменем і тим самим (за можливості) значенням ідентифікатора. Єдиним учасником такої групи спочатку є сам користувач, і ця група стає його **primary group**. Така схема використовується в Ubuntu, Debian, Fedora, RHEL та більшості сучасних дистрибутивів.

У дистрибутивах без UPG нові користувачі за замовчуванням потрапляють у загальну групу `users`, і всі вони автоматично мають спільну основну групу.

Коли UPG доцільно використовувати:

* коли потрібно, щоб файли нового користувача за замовчуванням не були доступні іншим: група-власник файлу - це його приватна група, у якій більше нікого немає;
* коли на машині працює багато користувачів і потрібна гранульована розмежованість доступу;
* коли для спільної роботи створюються окремі групи проєктів (кожен користувач має власну UPG як основну і додається до групи проєкту як до додаткової);
* для безпечнішого значення `umask 002`: файли доступні для запису групі, але група містить лише власника.

### 4.2. Якими командами можна створити групи користувачів? Наведіть приклади

* `groupadd` - основна низькорівнева команда, потребує прав root.

```bash
sudo groupadd developers          # створити групу, GID призначається автоматично
sudo groupadd -g 2000 testers     # створити групу з конкретним GID
sudo groupadd -r service_grp      # створити системну групу
```

* `addgroup` - зручніша обгортка (Debian/Ubuntu), працює інтерактивніше:

```bash
sudo addgroup students
```

* Також групу можна створити прямим редагуванням `/etc/group` через `vigr` (не рекомендується для початківців).

Перевірити результат можна так:

```bash
grep developers /etc/group
getent group developers
```

### 4.3. Якими командами можна змінити налаштування груп користувачів? Наведіть приклади

* `groupmod` - змінити назву групи (`-n`) або її GID (`-g`):

```bash
sudo groupmod -n clerks sales     # перейменувати групу sales у clerks
sudo groupmod -g 2500 clerks      # змінити GID групи
```

> Перейменування групи безпечне для доступу до файлів, оскільки файли належать GID, а не назві. А от зміна GID призведе до того, що файли залишаться належати «осиротілому» старому GID.

* `usermod` - змінити групи конкретного користувача:

```bash
sudo usermod -aG developers alex  # додати до додаткової групи (-a = append)
sudo usermod -g developers alex   # змінити primary group
sudo usermod -G a,b,c alex        # ЗАМІНИТИ весь список додаткових груп
```

* `gpasswd` - керування складом групи:

```bash
sudo gpasswd -a alex developers   # додати користувача в групу
sudo gpasswd -d alex developers   # прибрати користувача з групи
sudo gpasswd -A alex developers   # призначити адміністратора групи
```

* `groupdel` - видалити групу:

```bash
sudo groupdel developers
```

* `newgrp` - тимчасово змінити поточну основну групу в сесії:

```bash
newgrp developers
```

# Відповіді на контрольні запитання

**1. Чому в конфігураційних файлах паролі не зберігаються в явному вигляді?**

Файл `/etc/passwd` доступний для читання всім користувачам (він потрібен, наприклад, для зіставлення UID з іменем), тому в ньому в полі пароля стоїть `x`. Самі паролі зберігаються у файлі `/etc/shadow`, доступному лише root, і **не в явному вигляді, а у вигляді хешу** (з сіллю - salt, наприклад `$y$`, `$6$`). Хеш-функція одностороння: з хешу не можна відновити пароль, а при вході система хешує введений пароль і порівнює результати. Тому навіть витік файлу не дає пароль напряму, а сіль робить неефективними таблиці готових хешів.

**2. Чому не рекомендується виконувати повсякденні операції, використовуючи обліковий запис root?**

* Користувач root може все, тому одна помилкова команда (наприклад, `rm -rf` у не тому каталозі) може зруйнувати систему.
* Усі програми сеансу (браузер, поштовий клієнт, графічне середовище) працюватимуть із правами root, а значить, будь-яка вразливість чи шкідлива програма отримає повний контроль.
* Можна забути вийти з сеансу root.
* Немає журналу, хто саме і що виконував; `sudo` залишає записи в журналі.

Тому в Ubuntu вхід під root за замовчуванням вимкнено.

**3. У чому відмінність механізмів отримання особливих привілеїв `su` і `sudo`?**

* `su` перемикає на іншого користувача (за замовчуванням root) і **вимагає пароль цільового користувача** (root). Після цього весь сеанс виконується з його правами, доки не буде `exit`.
* `sudo` виконує **одну команду** з підвищеними правами і **вимагає пароль самого користувача**. Права налаштовуються в `/etc/sudoers` (можна дозволити лише окремі команди), а кожна дія записується в журнал. Пароль root не потрібно ні знати, ні мати.

**4. Чому домашній каталог користувача root не розміщено в каталозі `/home`?**

Каталог `/home` часто розміщується на **окремому розділі** чи на мережевому сховищі. Якщо цей розділ не змонтовано (збій, ремонт файлової системи, single-user режим), root усе одно має мати можливість увійти й виправити систему. Тому домашній каталог root - `/root` - розміщується в кореневій файловій системі.

**5. Для чого використовується команда `getent`?**

`getent` (*get entries*) звертається до баз даних, налаштованих у `/etc/nsswitch.conf` (`passwd`, `group`, `shadow`, `hosts`, `services` тощо), і виводить записи з **усіх джерел**: локальних файлів, а також LDAP, NIS тощо. На відміну від `grep` по `/etc/passwd`, показує і мережевих користувачів/групи. Приклад: `getent passwd root`, `getent group sudo`.

**6. Як можна змінити пароль користувача?**

* Свій пароль: `passwd`.
* Пароль іншого користувача (від root): `sudo passwd username`.
* Пакетно (зі списку `user:password`): `chpasswd`.
* Примусова зміна при наступному вході: `sudo passwd -e username` або `sudo chage -d 0 username`.

**7. Яким чином можна видалити існуючі групи користувачів? Чи залишиться інформація про них десь у системі?**

Групу видаляють командою `sudo groupdel groupname`. Видалити групу, яка є **primary group** якогось існуючого користувача, не можна - спочатку треба змінити йому основну групу або видалити користувача.

Після видалення запис зникає з `/etc/group` і `/etc/gshadow`, а членство користувачів у ній припиняється. Проте **файли та каталоги, якими володіла ця група, залишаються** - у них лише лишається числовий GID без імені групи (у `ls -l` відображається число). Тому їх треба перевірити (`find / -nogroup`) і виправити (`chgrp`).

**8. Яке призначення команди `chage`?**

`chage` (*change age*) керує **строком дії пароля та облікового запису**:

* `chage -l user` - показати поточні параметри;
* `-M days` - максимальний термін дії пароля;
* `-m days` - мінімальний інтервал між змінами;
* `-W days` - за скільки днів попереджати про закінчення;
* `-I days` - період неактивності після закінчення;
* `-E date` - дата закінчення дії акаунта;
* `-d 0` - змусити змінити пароль при наступному вході.

**9. Які параметри команди `usermod` ви вважаєте найбільш використовуваними?**

| Параметр | Призначення |
|---|---|
| `-aG group` | **додати** користувача до додаткової групи (завжди разом з `-a`) |
| `-G g1,g2` | задати **повний** список додаткових груп (замінює існуючі) |
| `-g group` | змінити основну групу |
| `-l newname` | змінити ім'я користувача |
| `-d /path -m` | змінити домашній каталог і перенести вміст |
| `-s /bin/zsh` | змінити shell |
| `-L` / `-U` | заблокувати / розблокувати обліковий запис |
| `-e YYYY-MM-DD` | встановити дату закінчення акаунта |
| `-c "comment"` | змінити коментар (GECOS) |
| `-u UID` | змінити UID |

Найчастіше використовую `-aG` (додавання в групи), `-s`, `-L/-U`.

## Conclusions

During this laboratory work we studied the basics of system and user security in Linux and practiced creating and managing users and groups from the Bash command line. We learned that administrative tasks should be performed through `sudo` rather than by working as root, because it limits the risk of mistakes and leaves an audit trail in the logs. We examined the structure of `/etc/passwd`, `/etc/shadow` and `/etc/group`, and understood why password hashes are stored separately from public account data.

In the practical part we displayed user information with `id`, `grep` and `getent`, and compared `who`, `w` and `last`: `who` shows only current sessions, `w` adds running processes and system load, and `last` provides the login history. We created three groups (`super_admins`, `noob_users`, `good_students`) and three users with passwords, assigned them to groups with `usermod -aG`, and verified the result using `getent group`. We also confirmed that `userdel` automatically removes a user (and their User Private Group) from all groups, while the groups themselves remain until they are removed with `groupdel`.

The most important practical lessons are: always use `-a` together with `-G` in `usermod`, remember that files belong to numeric UID/GID values and not to names, and check the result of every change in `/etc/group` and `/etc/passwd`. The goals of the work were achieved.
